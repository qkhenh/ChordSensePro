\section{Introduction}

\subsection{Motivation}

Music plays an important role in human life. Many people want to learn a musical instrument, such as piano or guitar. However, one big problem they face is that they cannot easily understand the chords in a song they want to practice. When a musician listens to a recording, they usually need to figure out the chord progression by ear. This takes a lot of time and skill, and it is difficult for beginners.

Existing tools such as Chordify and ChordAI can automatically detect chords from audio. However, they have clear limitations:
\begin{itemize}
    \item They show only the chord name (for example, ``Am'') but do not explain what that chord \emph{means} in the context of the song --- such as its harmonic function (Roman numeral: I, IV, V) or what scale a musician should use to improvise over it.
    \item They do not provide a complete practice environment. A musician still needs to use separate tools for a metronome, a media player, and a chord reference book.
    \item They do not handle extended chords (9th, 11th, 13th) well. These are common in jazz, ballads, and Vietnamese pop music (V-Pop), but existing tools often misclassify them as simpler triads.
    \item They do not support correction. If the AI makes a mistake, the user cannot fix it and save the corrected version.
\end{itemize}

These gaps motivated the development of \textbf{ChordSense Pro}: a unified AI-powered platform that not only detects chords accurately, but also provides harmonic analysis and a complete interactive practice workspace in one place.

\subsection{Objectives}

The main objectives of ChordSense Pro are:
\begin{enumerate}
    \item Build an end-to-end AI pipeline that accepts a song (from an uploaded audio file, a live microphone recording, or an external stream such as a YouTube or SoundCloud link), runs source separation, beat tracking, and chord recognition, and returns a complete chord event timeline.
    \item Fine-tune the \textbf{MERT-v1-330M} model using a \textbf{Cascaded 3-Head LoRA} architecture to improve recognition accuracy on extended chords (7th, 9th, 11th, 13th), especially on Vietnamese piano audio.
    \item Implement a \textbf{Client-Side Harmonic Engine} in the browser that automatically maps each detected chord to its Roman numeral function and recommends a compatible improvisation scale --- with zero server round-trip.
    \item Develop a synchronized \textbf{Interactive Practice Workspace} with a Smart Grid (beat-aligned chord display), A/B Loop, metronome, speed shift, and Chord Dictionary.
    \item Allow users to override AI-detected chords (Edit Marker) and save personalized playlists to the cloud.
\end{enumerate}

\subsection{Scope}

The project covers the following areas:
\begin{itemize}
    \item \textbf{AI Model Scope:} The primary instrument is \textbf{piano}. Piano has a well-defined acoustic model and abundant training data. Guitar is considered an optional extension if time permits.
    \item \textbf{Chord Vocabulary:} Basic triads (major, minor, diminished, augmented), dominant and major 7th chords, and extended chords up to the 13th (9th, 11th, 13th, suspended, altered).
    \item \textbf{Data Sources:} Academic datasets with open licenses (McGill Billboard, JAAH, ChoCo, RWC, Kaggle), plus a custom Vietnamese Piano Extended Chord Dataset recorded by the authors.
    \item \textbf{Platform:} A web application (React.js front end + Python FastAPI back end) containerized with Docker Compose.
    \item \textbf{Out of scope:} Real-time instrument tuning, score generation from scratch (sheet music export is a future feature), and mobile native applications.
\end{itemize}

\subsection{Significance}

\subsubsection{Practical Significance}

ChordSense Pro directly solves the fragmented workflow that musicians face today. By combining automatic chord recognition, harmonic analysis, and practice tools in a single platform, the system:
\begin{itemize}
    \item Reduces the time a musician spends figuring out chords in a song from hours to under one minute (15--45 seconds of asynchronous processing for a typical song).
    \item Removes the need for separate apps (metronome, chord dictionary, media player) during a practice session.
    \item Provides real-time visual feedback during live instrument practice, helping learners identify and correct mistakes immediately.
    \item Supports Vietnamese pop and ballad music --- a genre that is underserved by existing international tools.
\end{itemize}

\subsubsection{Scientific Significance}

From a research perspective, the project makes the following contributions to the field of Music Information Retrieval (MIR):
\begin{itemize}
    \item \textbf{VN Piano Extended Chord Dataset:} A labeled dataset of Vietnamese piano recordings covering extended chord types (7th through 13th). This is the first dataset of its kind focused on Vietnamese harmonic characteristics, and it will be published for the research community.
    \item \textbf{Cascaded 3-Head LoRA for ACR:} A parameter-efficient fine-tuning strategy for MERT that decomposes chord prediction into three sequential heads (Root $\to$ Quality $\to$ Extension), where each head is conditioned on the output of the previous one. This directly addresses the spectral overlap problem in extended chord recognition.
    \item \textbf{Client-Side Harmonic Engine:} A novel architecture choice that moves music theory computation entirely to the browser, eliminating network latency for harmonic analysis while keeping the AI inference server-side.
\end{itemize}

\subsubsection{Evaluation Method for Technology Selection}

Every major technology choice below is evaluated with a \textbf{weighted decision matrix}. Criteria are derived from the system requirements of Section~\ref{sec:proposed_system}, and weights sum to 100. Scores use a 5-point scale (1 = poor, 5 = excellent). The scores are \emph{analytical engineering judgements} supported by the cited documentation and by the reasoning stated beside each table; they are not measurements, and where a decision is sensitive to a weight, the sensitivity is reported explicitly. Results that depend on unmeasured performance are listed as validation actions rather than presented as facts.

\subsubsection{Front-End UI and Audio Runtime}\label{sec:fe_eval}

The front end must (i) keep a long-lived \texttt{AudioContext} and \texttt{MIDIAccess} session alive while the user navigates, (ii) update a Smart Grid of several hundred cells in step with playback, and (iii) remain cheap to host and operate. \textbf{Evidence and reasoning.}
\begin{itemize}
    \item \textbf{F1 --- Persistent audio state.} The Next.js App Router reference states that layouts do not re-render when navigating between pages, and that navigating across multiple root layouts causes a full page load~\cite{nextjs_layouts}. Next.js therefore \emph{can} satisfy F1: a client component placed in a persistent layout can keep an \texttt{AudioContext} alive during client-side navigation. It scores one point lower only because the audio service must be confined to a client component beneath server-rendered boundaries, and a full page load (a hard reload, or navigation across root layouts) discards it. Frameworks that run purely on the client (React SPA, Vue, Svelte, vanilla) own a single JavaScript runtime and are unaffected.
    \item \textbf{F2 --- Render latency.} The critical path (playhead $\to$ highlighted bar; \texttt{noteOn} $\to$ chord label) executes in the browser for every candidate, so server rendering gives no advantage. Svelte compiles components to direct DOM updates without a virtual DOM, and vanilla JavaScript has no abstraction cost; React and Vue pay a reconciliation cost. In React this is mitigated by keeping the per-frame playhead outside React state (updating one element through a ref or CSS transform) and by memoizing bar cells. Next.js adds hydration of the initial tree, hence a lower score. The absolute figures have \emph{not} been measured; they are a validation action (see below).
    \item \textbf{F3 --- Cost and operations.} A Vite build produces static assets that can be served by a CDN (the cost model of Table~\ref{tab:op_costs} assumes the free Cloudflare plan). Next.js with SSR requires a Node.js runtime or a serverless platform in front of FastAPI, adding a tier to deploy, monitor, and secure. A statically exported Next.js application would remove this cost but would then be a React SPA carried by a larger framework.
    \item \textbf{F4 --- Ecosystem and team fit.} The repository already contains a React~19 and Vite landing page, the team has two engineers, and the largest pool of audio, music-notation, and UI components exists for React. Svelte and vanilla JavaScript would require re-implementing modals, forms, and state management by hand or learning a smaller ecosystem.
    \item \textbf{Framework-independent audio engine.} The Harmonic Engine, the MIDI chord detector, and the Web Audio scheduler are written as plain TypeScript modules with no React imports. This isolates the most latency-critical code from the UI framework, which lowers the cost of changing the UI layer later.
\end{itemize}

\textbf{Conclusion and sensitivity.} React~19 with Vite is selected (4.65). \emph{Next.js is rejected under every weighting tested}, because its main benefits (indexable HTML and server-rendered first paint) do not apply to an authenticated workspace, while its costs (extra runtime tier, hydration) do. However, the analysis shows honestly that if team familiarity (F4) were ignored, \emph{Svelte would rank first} (4.88) because of its update model, so React is chosen for team and ecosystem reasons rather than for superior raw rendering performance. \textbf{Validation action:} before the Smart Grid design is frozen, a one-day spike that renders 400 bar cells with a 60\,fps playhead in React and in Svelte will be measured against NFR-01; if React fails the budget on a mid-range laptop, the grid (not the application) will be re-implemented with imperative DOM updates. Accepted trade-offs of the SPA: no server-rendered first paint for in-app pages, and a larger initial JavaScript payload (mitigated by route-level code splitting and lazy loading of ONNX Runtime Web and Soundfonts). The marketing landing page remains a separate static build where search visibility matters.

\subsubsection{Backend Gateway and API}\label{sec:be_eval}

The gateway authenticates users, enforces tier and class entitlements, accepts ingestion requests, tracks job state, serves chord timelines stored as PostgreSQL JSONB, and pushes completion events over WebSocket. It does not run GPU inference itself: heavy work is dispatched to separate workers through a queue. Five candidates were compared: Python FastAPI with asyncpg; Django (with Django REST Framework and Channels); Flask; Node.js (Express or NestJS); and Go (Fiber).

\textbf{Evidence and reasoning.}
\begin{itemize}
    \item \textbf{B1 --- Non-blocking I/O.} The gateway workload is dominated by connections that wait (job notification sockets) and by short database calls. FastAPI runs on ASGI with native \texttt{async}/\texttt{await} and has first-class WebSocket endpoints. Django needs Channels and a channel layer for WebSockets, and much of its ORM remains synchronous. Flask is WSGI-based and needs extensions (for example gevent-based Socket.IO) for sockets. Node.js and Go are event-loop and goroutine based and score highest.
    \item \textbf{B2 --- JSONB access cost.} asyncpg is a natively asynchronous PostgreSQL driver that uses the binary protocol. Two practical findings qualify the often-quoted speed claims. First, the asyncpg maintainers report large speed-ups over other drivers~\cite{asyncpg_readme}, but this is a vendor result, and an independent single-author comparison found that asyncpg was faster on concurrent primary-key lookups and inserts yet slower on bulk reads than psycopg~3~\cite{asyncpg_psycopg_blog}; the evidence is therefore mixed and workload-dependent. Second, asyncpg returns a \texttt{jsonb} value as raw JSON text unless a type codec is registered (SQLAlchemy's asyncpg dialect installs one). The design exploits this: because a chord timeline is read as a whole and forwarded unchanged to the browser, the gateway returns the JSON text directly as the response body and \emph{avoids parsing and re-serializing tens of kilobytes in Python}; parsing is performed only when a chart is edited or validated. psycopg~3 (async) is the closest alternative and is kept possible by hiding the driver behind a repository port.
    \item \textbf{B3 --- AI ecosystem and code sharing.} PyTorch, PEFT, Librosa, Demucs, and madmom are Python libraries, and the data engineering pipeline in this repository is Python. A Python gateway does \emph{not} import these heavy libraries (inference runs in separate workers), but it shares the Pydantic models of the chord vocabulary, chord event schema, and entitlement policy with the workers and the pipeline, so the same validation rules exist once. A Node.js or Go gateway would need a bridge (HTTP, gRPC, or a queue protocol) and a second implementation of these rules.
    \item \textbf{B4 --- Typed contract.} FastAPI validates requests and responses with Pydantic~2 and generates an OpenAPI specification automatically, which the React client and the tests consume. Django REST Framework achieves the same with more boilerplate; Flask requires assembling libraries.
    \item \textbf{B5 --- Throughput.} Go and Node.js provide higher raw throughput than CPython, whose Global Interpreter Lock limits CPU-bound parallelism within one process. Published framework comparisons are workload-dependent and often vendor-authored: for example, the Fiber project's own benchmark table reports Express ahead of Fiber on the multiple-queries test~\cite{fiber_benchmarks}, while the FastAPI documentation itself notes that such comparisons depend on how frameworks are grouped and tested~\cite{fastapi_benchmarks}. The throughput score is therefore based on architecture, not on a cited number.
\end{itemize}

\textbf{Conclusion and sensitivity.} FastAPI with asyncpg is selected (4.30). Raw throughput is not the binding constraint, because every analysis request is followed by 15--45 seconds of GPU work and the gateway is horizontally scalable and stateless. The decision rests mainly on B3 and on team size: \emph{if the team were polyglot, Go would rank first} (4.47 without B3) and would be the right choice for a gateway exceeding the load of this project. Accepted trade-offs: CPython throughput is lower, so the gateway is scaled by adding instances; the type codec behaviour of asyncpg must be handled explicitly; and Django's ready-made administration site is not used because role-, tier-, and class-based entitlement logic and two separate administrative consoles must be built regardless. \textbf{Validation action:} the load test of NFR-07 (100 concurrent users) will be run against the gateway before release; failing it would trigger scaling out first and a language change only as a last resort.

With two engineers and an infrastructure budget of roughly \$220--\$590 per month, this overhead is not justified by any requirement. The only component with a different scaling profile, GPU inference, is already isolated behind a queue as a worker.

Serverless \emph{GPU workers} remain compatible with the chosen style (the cost model already assumes one), so the selected architecture is a hybrid: a monolithic gateway with an elastic worker.

\textbf{Conclusion and sensitivity.} The modular monolith scores highest (4.60). Microservices would only overtake it if the organisation grew to several teams needing independent deployment (A5 and team autonomy dominating) or if one domain (for example the Classroom context) needed a very different scaling profile; neither holds for this project. Because the module boundaries are expressed as ports in the domain layer, extracting a module later (for example Ingestion) is possible without redesign. Accepted trade-offs: a single failure domain for non-GPU code (mitigated by stateless instances behind a load balancer), a shared database schema that requires discipline, and the need to enforce module boundaries by code review and import-rule checks.

\subsection{Key Architectural Concepts}

\subsubsection{Domain-Driven Design (DDD)}\label{sec:ddd}

The data engineering pipeline and the gateway modules are organized using \textbf{Domain-Driven Design (DDD)} with the Onion Architecture pattern. Each major concern is isolated into its own \textit{Bounded Context} with three internal layers:
\begin{itemize}
    \item \textit{Domain Layer:} Pure business entities and interface contracts (Python \texttt{Protocol} classes). No framework dependencies.
    \item \textit{Application Layer:} Orchestration logic and service classes that coordinate domain objects.
    \item \textit{Infrastructure Layer:} Concrete implementations --- PostgreSQL repositories, MongoDB clients, external API adapters.
\end{itemize}

\subsubsection{Chain of Responsibility Pattern}

The audio processing pipeline uses the \textbf{Chain of Responsibility} pattern. Seven processing handlers are wired into a chain. Each handler reads from and writes to a shared \texttt{ProcessedAudio} data object, then passes it to the next handler. Adding or removing a processing step only requires inserting or removing a handler, without touching any other part of the pipeline.

\subsubsection{Ports and Adapters (Hexagonal Architecture)}

The data loading module defines abstract \texttt{Downloader} port interfaces. Concrete implementations (e.g., \texttt{JaahDownloader} using yt-dlp, \texttt{LocalFileDownloader} using file copy) are plugged in as adapters. This allows domain logic to be tested without real network connections or database access.

\subsubsection{Event-Based JSONB Timeline}\label{sec:jsonb_timeline}

Song chord data is stored as an event-based absolute timeline in a JSONB column, not as a fixed grid. This design choice ensures that changing the tempo or time signature never corrupts the stored chord sequence. Each event records an absolute timestamp in milliseconds along with chord attributes, so the front end can re-render the grid at any tempo.

This chapter introduced the full technology stack and compared the candidate front-end, backend, and architectural options with weighted decision matrices, including a sensitivity analysis that shows where a different weighting would change the outcome (for example, Svelte on rendering alone, or Go for a polyglot team). The combination of DDD, Chain of Responsibility, and Hexagonal Architecture provides a clean separation of concerns inside a modular monolith and allows each module to evolve independently. The decision to place music theory computation and MIDI chord detection on the client side removes the network from the real-time path, which is the most common source of latency in interactive practice tools. \section{Related Works}

\subsection{Existing AI Models for Automatic Chord Recognition}

Automatic Chord Recognition (ACR) has evolved through three main technological phases:

\subsubsection{Template-Based Methods and Hidden Markov Models (2005--2014)}

Early systems computed 12-dimensional chromagrams from audio and matched them against hand-crafted chord templates using cosine similarity. Hidden Markov Models (HMMs) were then applied to model chord transition probabilities and smooth the frame-level predictions. While computationally simple, these methods were rigid and performed poorly on chords with complex voicings. The chromagram representation cannot distinguish chords that share the same pitch classes (for example, Am7 and C6 contain exactly the same four notes).

\subsubsection{Deep Convolutional and Recurrent Networks (2016--2020)}

Convolutional Neural Networks (CNNs) trained on log-frequency spectrograms significantly improved triad detection accuracy. Bidirectional LSTMs were later added to capture temporal context. However, performance on extended chords remained limited because standard pop music datasets contain far more basic triads than extended chord examples, and the models were trained in a flat classification setting over many chord classes simultaneously.

\subsubsection{Pre-Trained Foundation Transformers (2023--Present)}

Large-scale self-supervised audio models, such as MERT pre-trained on 160,000 hours of music audio, capture rich representations of pitch, timbre, and harmony. These models can be adapted to downstream MIR tasks via parameter-efficient fine-tuning with strong results. Recent architectures such as \textbf{Chordformer} (Conformer-based, 2024) and \textbf{BACHI} (Boundary-Aware Hierarchical Chord Inference, 2024) represent the current state of the art. BACHI's hierarchical decoding --- detecting boundaries first, then predicting root, quality, and bass separately --- directly inspired the Cascaded 3-Head design in ChordSense Pro.

\section{Proposed System}\label{sec:proposed_system}

\subsection{Business Context}

Musicians and learners who practice with digital recordings face four recurring problems in their daily workflow.

\textbf{Problem 1 --- No Harmonic Context.} Existing chord detection tools output raw chord labels (e.g., ``Am'', ``F'') but provide no information about what these chords \emph{mean} in the key of the song. A musician cannot easily see that ``Am'' is the tonic (i), ``F'' is the submediant (VI), or that ``E'' is acting as a secondary dominant --- insights that are critical for improvisation and arrangement.

\textbf{Problem 2 --- Fragmented Practice Workflow.} A musician who wants to learn a song by ear typically uses four separate tools at the same time: a media player (to listen), a chord chart app (to see the chords), a standalone metronome (to keep time), and a chord fingering reference (to learn new shapes). ChordSense Pro replaces all of these with a single integrated workspace.

\textbf{Problem 3 --- Rigid AI Output.} When an AI tool produces an incorrect chord label, there is no way to fix it and save the correction for future sessions. Musicians also frequently need to toggle between a simplified chord view (e.g., ``G'' instead of ``G9sus4'') and a precise extended view --- a toggle that currently requires a server round-trip in all competing products.

\textbf{Problem 4 --- Poor Extended Chord Support for Vietnamese Music.} Extended chord recognition (9th, 11th, 13th) is particularly weak for Vietnamese pop and ballad music. International training datasets do not reflect the harmonic patterns common in V-Pop arrangements, and no existing tool has published a Vietnamese chord recognition dataset.

Seat reassignment is allowed (for example between semesters) but limited per month.

\textbf{Enrollment methods.}
\begin{itemize}
    \item \textbf{E-mail invitation:} The Teacher enters addresses; each student receives a single-use link that expires after 7 days.
    \item \textbf{Class Code:} A random code that students enter after registration. It can expire, be rotated, be limited to the number of free seats, and optionally require Teacher approval.

Because many students are minors, the enrollment flow records consent of a guardian where the applicable regulation requires it (for example, Vietnam's Decree~13/2023/ND-CP on personal data protection, and the GDPR for users in the European Union).

\textbf{Devices.} The Teacher mainly uses a laptop to prepare and teach. Students practise on laptops, tablets, or with a digital piano at home. Web MIDI is not available in every browser: Chromium-based browsers and Firefox support it, but Safari does not~\cite{chrome_webmidi}, and browsers on iPad and iPhone use the WebKit engine. Tablet students without Web MIDI therefore fall back to microphone practice or the on-screen keyboard, and the Education plan description states this limitation openly.

\textbf{Education-specific features.}
\begin{itemize}
    \item \textbf{Shared Class Repertoire:} The Teacher builds a repertoire list (songs, assigned loop regions, target tempo, optional due date). Publishing it synchronizes the list to every enrolled student's workspace within seconds through the WebSocket channel; students who are offline receive it on reconnection. Songs that were already analysed are served from the cache.

The server marks the master layer read-only for students; students keep a private personal layer for their own notes. The layers are separate JSONB documents, so a student's edit can never overwrite the master.
    \item \textbf{Practice Telemetry and Tracking Dashboard:} The client records practice time (with idle detection), the number of A/B Loop repetitions, and chord accuracy (target chord versus played chord) from Web MIDI or microphone practice. Events are batched and sent periodically. The Teacher sees per-student and class-level views. Only results are uploaded: no raw microphone audio and no raw MIDI stream is sent for telemetry, only the correctness flag and timestamps, and students can see what is collected.
\end{itemize}

The overall flow from the user's perspective is:

\subsubsection{Research Problems}

\subsubsubsection{Music Theory Foundation: Chords, Harmony, and Extended Voicings}

A \textbf{chord} is a set of notes sounded together. Chords are built by stacking intervals (usually thirds) above a \textit{root note}. The simplest chord is a \textbf{triad}: root, third, fifth. The most common triad types are major (bright sound) and minor (darker sound).

\textbf{Extended chords} add further notes above the triad. A 7th chord adds the seventh interval; a 9th chord adds the ninth; an 11th chord adds the eleventh; and a 13th chord adds the thirteenth. These chords are common in jazz, soul, neo-soul, and Vietnamese ballads. They create richer, more complex sounds that are harder to detect automatically because their additional notes often overlap with the notes of simpler chords.

\textbf{Roman numeral analysis} describes how each chord functions within a key. In the key of A minor, the chord Am is the tonic (i), the chord E is the dominant (V), and the chord F is the submediant (VI). This information tells a musician how the song ``moves'' harmonically and which scale to use for improvisation.

\paragraph{Jazz Harmony and Extended Chord Theory (Reference: Berklee / Levine)}

In jazz theory, as described in \emph{The Berklee Book of Jazz Harmony} and Mark Levine's \emph{The Jazz Theory Book}, chords are identified by their interval structure, note types, and harmonic role.

\textbf{The jazz basic unit.} In classical music, the basic chord is a three-note triad. But in jazz, the \textbf{seventh chord} (four notes: Root, 3rd, 5th, 7th) is the basic building block. A jazz chord has three types of notes:
\begin{itemize}
    \item \textbf{Chord Tones (1, 3, 5, 7):} These notes set the main sound of the chord --- major, minor, dominant, or diminished.
    \item \textbf{Tensions / Extensions (9, 11, 13):} These notes are added on top of the seventh to give the chord a richer, more colourful sound.
    \item \textbf{Chord-Scale Relationship:} A chord is a vertical stack of notes played together. A chord scale is those same notes spread out horizontally across one octave --- used for melody and improvisation.
\end{itemize}

\textbf{Step 1 --- Find the Root.} The first letter in the chord symbol (e.g., \textbf{C}, \textbf{E$\flat$}, \textbf{F$\sharp$}) is the root note. In a slash chord (e.g., G/C), the letter before the slash is the chord above, and the letter after the slash is the bass note.

\textbf{Step 2 --- Identify Chord Quality.} The 3rd and 7th notes decide the chord's quality. The 5th can usually be left out without changing how the chord sounds. The three main seventh-chord types are:
\begin{itemize}
    \item \textbf{Major 7th (Maj7, $\Delta$):} Major 3rd + Major 7th. Notes: 1 -- 3 -- 5 -- 7. Example: C$\Delta$7 = C -- E -- G -- B.
    \item \textbf{Minor 7th (m7, $-$7):} Minor 3rd + Minor 7th. Notes: 1 -- $\flat$3 -- 5 -- $\flat$7. Example: Cm7 = C -- E$\flat$ -- G -- B$\flat$.
    \item \textbf{Dominant 7th (7):} Major 3rd + Minor 7th. Notes: 1 -- 3 -- 5 -- $\flat$7. Example: C7 = C -- E -- G -- B$\flat$.
\end{itemize}
Other chord types include: Suspended (sus4/sus2), Half-Diminished ($-7\flat5$, $\varnothing$), and Fully Diminished ($^\circ$7).

\textbf{Step 3 --- Find the Tensions.} Numbers after the chord quality symbol show the added extension notes:
\begin{itemize}
    \item \textbf{Natural tensions:} 9, 11, 13.
    \item \textbf{Altered tensions:} $\flat$9, $\sharp$9, $\sharp$11, $\flat$13.
    \item Example: C7($\flat$9, $\sharp$11) is a Dominant 7 chord on C (C -- E -- G -- B$\flat$) with two extra notes: D$\flat$ ($\flat$9) and F$\sharp$ ($\sharp$11).
\end{itemize}

\textbf{Step 4 --- Harmonic Function.} A chord always works as part of a progression. Knowing where it sits in a common pattern --- such as \textbf{II--V--I} --- tells us its role:
\begin{itemize}
    \item \textbf{Minor 7th ($-$7):} Usually works as \textbf{II} (the chord before the dominant).
    \item \textbf{Dominant 7th (7):} Usually works as \textbf{V} (creates tension that wants to resolve to the tonic).
    \item \textbf{Major 7th (Maj7):} Usually works as \textbf{I} (the home chord, stable and resolved).
\end{itemize}

This four-step method is the basis for ChordSense Pro's \textbf{Client-Side Harmonic Engine}. The engine breaks each chord into Root, Quality, and Extensions (Steps 1--3), then finds its Roman numeral role in the song's key (Step 4).

\subsubsubsection{AI Model Research Problems}

The core research challenge is building a model that reliably recognizes extended chords from piano audio. The following are the key technical problems:

\textbf{Extended chord overlap:} Am7 (A--C--E--G) and C6 (C--E--G--A) contain exactly the same four pitch classes. Their chroma vectors are identical. A flat classification model cannot distinguish them without knowing the harmonic context (root and bass note in the progression).

\textbf{Data imbalance:} In standard pop music datasets, basic major and minor triads appear thousands of times more often than extended chords. A model trained on imbalanced data will predict ``Am'' when the correct answer is ``Am9'' because it has seen many more ``Am'' examples.

\textbf{Polyphonic interference:} In a full band recording, drums, bass, and vocals all overlap with the harmonic instrument. The 9th or 11th extension tones --- which are acoustically weaker than the root, third, and fifth --- are easily masked by other instruments.

\textbf{Chord flickering:} Frame-by-frame prediction produces noisy sequences such as [C, C, Am, C, C] where the single ``Am'' frame is likely an error. Post-processing smoothing is required to produce musically coherent output.

\subsubsection{Challenges and Difficulties}

\begin{itemize}
    \item \textbf{Spectral ambiguity of extended chords:} Am7 and C6 are acoustically identical --- only the harmonic context identifies which is correct. The Cascaded 3-Head architecture addresses this by conditioning the Extension head on the predicted Root and Quality.
    \item \textbf{Class imbalance in training data:} Basic triads outnumber 9th and 11th chords by more than 100:1 in standard datasets. Focal Loss and pitch-shift augmentation are used to balance training.
    \item \textbf{Multi-instrument polyphony:} Demucs source separation is used to isolate the harmonic stem before inference, removing drum and vocal interference.
    \item \textbf{Real-time inference latency:} The full MERT-v1-330M model is far too large for interactive use: a single server-side inference pass cannot meet an interactive budget once network round-trip and audio windowing are included. The microphone-based Real-Time Practice Mode therefore targets a $<$200\,ms feedback latency only \emph{conditionally}, using a distilled, int8-quantized ONNX model executed on the client (ONNX Runtime Web with WebAssembly or WebGPU). By contrast, the Web MIDI path avoids audio inference altogether and is deterministic.
    \item \textbf{Two latency domains:} The system separates \emph{client-side interactive synchronization} (Smart Grid rendering, Web Audio playback, Web MIDI; budget of 50--100\,ms) from the \emph{server-side asynchronous ingestion pipeline} (Demucs, madmom, MERT; 15--45 seconds for a 3--4 minute song, delivered through a job queue and WebSocket notification). Mixing these two domains in a single latency target would be technically unrealistic.
    \item \textbf{Vietnamese music under-representation:} Existing international datasets do not capture the chord patterns common in V-Pop. A dedicated Vietnamese Piano Extended Chord Dataset is recorded and used for fine-tuning in Phase 3 of training.
\end{itemize}

\subsubsection{Non-Functional Requirements}

The non-functional requirements are organized around two clearly separated \textbf{latency domains}, because a single latency figure cannot describe both:

\begin{itemize}
    \item \textbf{Client-side interactive synchronization} (Smart Grid rendering, Web Audio playback, Web MIDI input, Harmonic Engine recalculation). These operations run in the browser with no network in the critical path and are held to a real-time budget of \textbf{50--100\,ms}.
    \item \textbf{Server-side AI ingestion pipeline} (upload, recording, or external stream $\to$ Demucs $\to$ madmom $\to$ MERT + LoRA). This workload is GPU-bound and is therefore executed \textbf{asynchronously} through a job queue with WebSocket notification. A realistic end-to-end time is \textbf{15--45 seconds} for a 3--4 minute song; a server inference result in 100\,ms is not achievable and is not claimed.
\end{itemize}

Table~\ref{tab:nonfunctional_requirements} states, for every requirement, the measurable metric and the test condition under which it is verified. \emph{Feasibility} is an engineering judgement against the selected stack (High, Medium, or conditional on stated assumptions), and \emph{Priority} follows the delivery roadmap: \textbf{High} is Phase~1 (the core MVP, without which the system cannot run), \textbf{Medium} is Phase~2 (production readiness and scale), and \textbf{Low} is Phase~3 (secondary features and advanced optimization, scheduled for later). \textbf{Reading the priorities.} A requirement's priority is the priority of its \emph{metric}, not of the feature. \subsubsection{Data Requirements}

\begin{itemize}
    \item \textbf{User Data:} Credentials, profile information, roles, and plan or seat membership for authentication and access control.
    \item \textbf{Song Analysis Data:} Full chord event timeline per song --- timestamp, root, quality, extension, confidence, and user override status --- plus musical key, tempo, and time signature, stored as layered documents (AI baseline, master, personal) together with the content hash and source type (upload, recording, or external stream).
    \item \textbf{User Edit History:} All Edit Marker chord overrides per song per user, the lineage between a forked chart and its source, and personal custom chord palettes, enabling comparison between original AI output and user-curated versions.
    \item \textbf{Playlist Data:} User-defined playlists with ordered song references and custom metadata.
    \item \textbf{Class and Enrollment Data:} Classes, Teacher and Student seats, invitations, class codes, CSV import reports, guardian consent records, and shared repertoire lists.
    \item \textbf{Practice Telemetry:} Per-session records: practice duration, A/B Loop repetitions, target and recognized chord sequences, timestamps, and per-chord correctness flags, used for class dashboards and personal progress.
    \item \textbf{Subscription and Policy Data:} Plans, versioned policies (prices, quotas, seat limits), discount codes, and payment events used for revenue analytics.
    \item \textbf{Feedback Data:} User reports of wrongly recognized chords (detected chord, expected chord, genre note, model version, position), general feedback with optional screenshots, support requests, and the status history and replies of every ticket.
    \item \textbf{Operational and Audit Data:} Infrastructure metrics, rate-limit counters, and the append-only audit log.
    \item \textbf{AI Model Metadata:} Version-controlled LoRA adapter registry with accuracy metrics per chord class per model version.
    \item \textbf{Training Dataset:} VN Piano Extended Chord Dataset --- labeled audio segments mapped to chord labels (root, quality, extension) for model fine-tuning and evaluation.
\end{itemize}

\subsection{Chapter Summary}

Chapter~4 described the business problems that ChordSense Pro addresses, defined the four user groups, identified the core research challenges in automatic chord recognition, and specified all functional and non-functional requirements. Audio ingestion was generalized to three sources (file upload, microphone recording, external stream); the Free, Pro, and Education plans were distinguished by quota and entitlements, with the Education price derived from a unit-cost model; Web MIDI input was added as a zero-latency Human-in-the-Loop path; the Music Platform Manager and IT Administrator roles were separated by duty; and the non-functional requirements were separated into a client-side real-time domain (50--100\,ms) and a server-side asynchronous ingestion domain (15--45 seconds), each with measurable metrics and test conditions. Section~\ref{sec:fe_eval} onward in Chapter~2 contains the weighted technology evaluations that justify the stack. The next chapter translates these requirements into concrete system analysis and design decisions for the Front End and Back End components.

\subsubsection{Interaction Modeling --- Use Case Diagram}

The system has twenty use cases (UC-00 to UC-19), grouped as follows: core learning (UC-00 to UC-07, plus the Metronome and Rhythm Engine UC-18 and the user feedback loop UC-19), the Education package (UC-08 to UC-11), the Music Platform Manager (UC-12 to UC-14), and the IT Administrator (UC-15 to UC-17). Each use case describes how a user interacts with the system. The actors and interaction types are listed below.

\textbf{Actors:}
\begin{itemize}
    \item \textbf{Guest:} A visitor who has not logged in yet. They can sign up or log in.
    \item \textbf{Free User:} A user with a free account. They are limited to 5 song analyses per day, the basic Smart Grid, and local-only chord overrides (nothing is saved to the cloud).
    \item \textbf{Paid User (Pro):} A user with a paid subscription. They have unlimited ingestion, advanced A/B Loop, cloud-synchronized overrides, export, and peripheral instrument connection through Web MIDI.
    \item \textbf{Teacher:} The Master Admin of an Education class. They manage Student Seats, publish repertoire and master charts, and read the practice dashboard.
    \item \textbf{Student:} A member of a class. They practice the assigned repertoire with Pro practice features and a private personal layer.
    \item \textbf{Expert (Music Theory Advisor):} A music specialist who adds knowledge to the system.
    \item \textbf{Music Platform Manager (Music PM):} A business and content administrator who monitors revenue and usage, configures subscription policy, handles user feedback, and curates the chord dictionary. This role has no access to infrastructure.
    \item \textbf{IT Administrator:} A system operations administrator who manages infrastructure and datastores, protects the API gateway, monitors compute resources and audit logs, and deploys AI model updates. This role cannot change business policy.
\end{itemize}

\textbf{AI Interaction Types:}
\begin{itemize}
    \item \textbf{Human-on-the-Loop (HOTL):} The AI works by itself. The user checks the result and can fix it later. (Used in: song analysis, A/B Loop, Admin monitoring.)
    \item \textbf{Human-in-the-Loop (HITL):} The user reacts to system feedback in real time. (Used in: Real-Time Practice Mode and Web MIDI input. In the MIDI case the feedback is produced by the deterministic Client-Side Harmonic Engine, not by an AI audio model.)
\end{itemize}

Free users keep all changes in local browser storage; Paid users and Students are synchronized to the cloud; a Teacher edits the class master layer. \\ \hline
Preconditions &
\begin{itemize}[leftmargin=1em, nosep, topsep=2pt, partopsep=0pt, parsep=0pt, after=\strut]
    \item User is logged in
    \item A song analysis is open in the workspace
\end{itemize}
\\ \hline
Postconditions &
\begin{itemize}[leftmargin=1em, nosep, topsep=2pt, partopsep=0pt, parsep=0pt, after=\strut]
    \item \textbf{Success:} The chord is changed in the chosen target (current layer or a new forked chart); the Roman numeral and scale are recomputed within 50 ms; the AI baseline remains preserved. Changes are stored in the cloud for Paid users and Students, and in local browser storage only for Free users.
    \item \textbf{Failure:} An invalid chord is rejected with a message and the chart is unchanged.
\end{itemize}
\\ \hline
Basic Flow &
\begin{enumerate}[leftmargin=1.5em, nosep, topsep=2pt, partopsep=0pt, parsep=0pt, after=\strut]
    \item User clicks a chord cell; the Edit Marker opens and shows the detected chord (for example ``Cmaj9''), its pitch classes, and its Roman numeral
    \item Step 1, alternative names: the Engine computes on the client the equivalent views of the same harmony and lists them with their Roman numerals and match type. An Exact match has the same pitch classes (for example ``Em7/C'' for Cmaj9: E-G-B-D over the bass C). A Partial match omits a chord tone and says which (for example ``G/C'' omits the third E, so it is a Cmaj9 without 3rd). Enharmonic spellings (for example C\#maj7 and Dbmaj7) are ordered by the key signature. The user may click a suggestion
    \item Step 2, save strategy: the user chooses (A) In-place override, which writes to the current editable layer while the AI baseline stays preserved and ``Reset to AI'' remains available, or (B) Fork as New Chart, which creates a copy in the personal library with a link to the source chart and a version label, while the original chart stays unchanged
    \item Step 3, Chord Dictionary Picker: if no suggestion fits, the user opens the picker and selects Root, Quality, Tension/Extension, Alterations, and Slash Bass; a preview shows the fingering diagram and can be auditioned
    \item Step 4, Custom Chord Creator: if the dictionary has no suitable chord, the user selects notes on the Virtual Fretboard or Keyboard; the system lists the selected pitch classes and proposes a name if one matches, and the user may accept it or type their own symbol
    \item The Harmonic Engine derives the Roman numeral: if the pitch classes match a dictionary chord, its function is used; otherwise the scale degree of the chosen root (or the lowest note) in the song key is combined with the chord class given by its third and fifth, and the chord is marked ``custom''
    \item System validates the chord (at least one and at most twelve pitch classes, symbol not empty) and applies it to the chosen target
    \item The Smart Grid shows the new chord and annotations within 50 ms
    \item Persistence: for Paid users and Students the change is sent to the server in the background; for Free users it is written only to local browser storage; a Teacher's edit goes to the master layer and takes effect for Students when published (UC-09)
\end{enumerate}
\\ \hline
Alternative Flow &
\textbf{AF1: User selects ``Reset to AI''}
\begin{enumerate}[leftmargin=1.5em, nosep, topsep=2pt, partopsep=0pt, parsep=0pt, after=\strut]

\textbf{Design rules derived from the research.}
\begin{itemize}
    \item \textbf{Client-only real-time paths.} Web MIDI input, chord detection, the A/B Loop, the metronome, and the Basic/Precise toggle make no network request. The only network use of a MIDI session is the explicit ``Save session'' action.
    \item \textbf{Browser-recording normalization.} \texttt{MediaRecorder} produces different containers in different browsers (WebM/Opus in Chromium, Ogg or WebM/Opus in Firefox, MP4/AAC in Safari~\cite{webkit_mediarecorder}); the client therefore uploads whatever the browser produces and the server Normalizer converts it, instead of assuming one format.
    \item \textbf{Untrusted URLs.} External links are resolved by yt-dlp, whose generic extractor accepts any URL and therefore cannot tell in advance whether a link is supported; every fetch passes the SSRF guard of FR-20, and failure always leads back to upload or recording.
    \item \textbf{Policy outside the code.} Quotas and prices are read from the versioned policy of the Subscription and Policy context, so that the Music PM can change them without a release, while technical rate limits remain with the IT Administrator.
\end{itemize}

\subsubsection{Third-Party Policies and Data Handling}

\begin{itemize}
    \item \textbf{External stream download:} Audio from YouTube, SoundCloud, or a direct public URL is resolved with yt-dlp for personal, non-commercial music analysis, subject to the terms of the originating platform. The downloaded audio is processed server-side, deleted after processing, and not redistributed. The fetcher accepts only HTTP and HTTPS and rejects private, loopback, and link-local addresses.
    \item \textbf{Student and class data:} Practice telemetry contains only counts, durations, and correctness flags, is visible only to the Teacher of the class and the Student concerned, and is retained for at most 12 months. Guardian consent is recorded for minors where regulation requires it.
    \item \textbf{User audio data:} Microphone audio captured during Real-Time Practice Mode is processed in-memory for chord inference. A short 2-second audio clip is optionally stored in MongoDB with a 30-day TTL for model improvement, subject to user consent.
    \item \textbf{MIDI data:} Web MIDI messages are processed only in the browser and are never streamed to the server. Only a chart that the Paid User explicitly saves is uploaded (as chord events, not raw MIDI). The MIDI permission is requested without system-exclusive access.
    \item \textbf{Authentication:} JWT tokens with configurable expiry are used. Passwords are hashed with bcrypt before storage.
\end{itemize}

\subsubsection{Audio Acquisition Layer (data\_loader)}

This layer defines a \texttt{Downloader} Protocol (port interface). The \texttt{AudioDispatcher} acts as a registry: at startup, each concrete downloader is registered against its corresponding \texttt{AudioSource} enum value. When a download is requested, the dispatcher looks up the correct downloader and delegates the call.

The seven concrete downloader adapters and their data sources are:
\begin{itemize}
    \item \textbf{JaahDownloader} --- JAAH dataset: 113 jazz tracks from Zenodo (direct HTTP download).
    \item \textbf{McGillDownloader} --- McGill Billboard: 1,300 pop/rock tracks via yt-dlp YouTube search.
    \item \textbf{ChocoDownloader} --- ChoCo corpus: 20,000 tracks via yt-dlp YouTube URLs.
    \item \textbf{RwcDownloader} --- RWC Popular Music: 100 Japanese pop tracks (local archive copy).
    \item \textbf{KaggleDownloader} --- Kaggle Guitar Chord Dataset v3: 7,000+ recordings via Kaggle CLI.
    \item \textbf{PianoteqDownloader} --- Synthetic piano data rendered by the Pianoteq physical modeling synthesizer.
    \item \textbf{LocalFileDownloader} --- Local files already on disk (used for manual additions and testing).
\end{itemize}

\subsubsection{Orchestration Layer (data\_ingest)}

The Orchestration layer manages two services that correspond to the two ETL DAGs:
\begin{itemize}
    \item \textbf{IngestRawService (DAG 1):} Reads pending URLs from the \texttt{crawl\_queue} PostgreSQL table, calls \texttt{run\_data\_loader()} to download the WAV file, downloads any associated annotation file, and saves a \texttt{RawAudioJob} document to MongoDB. This is the Extract (E) phase.
    \item \textbf{ProcessAudioService (DAG 2):} Reads pending \texttt{RawAudioJob} documents from MongoDB, validates that the WAV file exists on disk, runs the training pipeline chain, and saves the completed \texttt{SongAnalysis} to PostgreSQL. Cleans up temporary files afterwards. This is the Transform + Load (T+L) phase.
\end{itemize}

MongoDB acts as a decoupling layer between DAG 1 and DAG 2. If a download fails, it does not block the processing of audio files that were already downloaded. DAG 2 can also be re-triggered without re-downloading any files.

\subsubsection{DAG 1: dag\_ingest\_raw (Extract) --- Every 2 Hours}

\begin{center}
\texttt{pick\_urls} $\to$ \texttt{download\_and\_stage} $\to$ \texttt{send\_summary} $\to$ \texttt{trigger\_dag\_process}
\end{center}

The DAG reads up to 10 pending rows from \texttt{crawl\_queue}, calls the \texttt{AudioDispatcher} to download each audio file, stages the \texttt{RawAudioJob} to MongoDB, and then fires \texttt{dag\_process\_audio} via a \texttt{TriggerDagRunOperator} (fire-and-forget, no wait).

\subsubsection{DAG 2: dag\_process\_audio (Transform + Load) --- Triggered by DAG 1}

\begin{center}
\texttt{pick\_pending\_jobs} $\to$ \texttt{process\_and\_save} $\to$ \texttt{send\_summary}
\end{center}

The DAG reads pending \texttt{RawAudioJob} documents from MongoDB and runs the full training handler chain on each one. The resulting chord timeline, detected key, and tempo are saved to the \texttt{song\_analyses} PostgreSQL table. Temporary WAV files and stems are deleted after a successful save.

\subsubsection{DAG 3: dag\_analytics\_rollup (Analytics) --- Nightly at 23:30}

\begin{center}
\texttt{aggregate\_attempts} $\to$ \texttt{rolling\_accuracy} $\to$ \texttt{update\_mastery}
\end{center}

This DAG aggregates all chord practice attempts recorded since the previous run, computes a rolling 3-day accuracy score per student per chord, and updates the \texttt{user\_chord\_mastery} table. This powers the student progress dashboard.

\subsection{Technology Choice: Database Selection}

The pipeline uses two databases. Each one is chosen for a specific stage, because the two stages have very different needs.

Some jobs have annotation file paths, others do not. Some have YouTube URLs, others point to local files. The staging database must accept all of these without requiring a fixed schema. It also needs to handle many fast writes, and it should be able to delete old data automatically when it is no longer needed.

\subsubsection{Final Storage: Why PostgreSQL?}

After DAG~2 finishes, the output data is clean and well-structured: a detected key, a tempo value, and a chord event timeline. This data is stored permanently and is read by the web application. The final database must support queries across multiple tables (users, songs, and practice logs), and it must make sure that user edits are never lost or only partially saved.

\section{AI Model --- Automatic Chord Recognition}

\subsection{MERT: Music Understanding Model}

\textbf{MERT} (Music Encoder Representation from Transformers) is a self-supervised pre-trained model designed for Music Information Retrieval tasks. It was developed by the Music AI Platform (m-a-p) research group and published at ICLR 2024.

Key facts about MERT-v1-330M:
\begin{itemize}
    \item \textbf{Pre-training data:} 160,000 hours of music audio from diverse genres.
    \item \textbf{Architecture:} A Transformer encoder similar to HuBERT, but with a multi-task self-supervised objective.
    \item \textbf{Teachers:} Two teacher signals are used during pre-training: an \textit{RVQ acoustic teacher} (captures timbre and pitch) and an \textit{MFCC teacher} (captures rhythm and temporal patterns). This combination makes MERT understand both the pitch content and the temporal structure of music.
    \item \textbf{Parameter count:} 330 million parameters.
    \item \textbf{Benchmark performance:} MERT achieves state-of-the-art or near-state-of-the-art results on 14 standard MIR benchmark tasks, including chord recognition, beat tracking, and pitch detection.
\end{itemize}

Why MERT is the best choice for this project:
\begin{itemize}
    \item It was specifically designed for local-level MIR tasks (predicting a label per time segment), which matches the chord recognition problem exactly.
    \item It outperforms comparable audio models (Music2Vec, CLAP, MusicBERT) on chord-level prediction benchmarks.
    \item It is available on HuggingFace as \texttt{m-a-p/MERT-v1-330M} and can be loaded in one line of Python.
    \item Fine-tuning can be done on a single GPU with LoRA, making it feasible for a student research project.
\end{itemize}

\subsection{LoRA: Low-Rank Adaptation}

\textbf{LoRA} (Low-Rank Adaptation) is a parameter-efficient fine-tuning technique. Instead of updating all 330 million parameters in the MERT backbone, LoRA \textit{freezes} the pre-trained weights and attaches small trainable adapter matrices to selected attention layers.

The mathematical principle is:
\[
    W_{\text{eff}} = W + \frac{\alpha}{r} \cdot A \cdot B
\]
where $W$ is the frozen pre-trained weight matrix, $A \in \mathbb{R}^{d \times r}$ and $B \in \mathbb{R}^{r \times d}$ are the trainable low-rank matrices, $r$ is the rank (a small number such as 8 or 16), and $\alpha$ is a scaling factor.

For a weight matrix of size $768 \times 768$ (589,824 parameters), using LoRA with $r=8$ only adds $(768 \times 8) + (8 \times 768) = 12,288$ trainable parameters --- a reduction of 98\%.

Advantages of LoRA for this project:
\begin{itemize}
    \item \textbf{Low VRAM requirement:} Training fits on a single RTX 3090 or Google Colab A100 (40\,GB).
    \item \textbf{Zero inference overhead:} Before deployment, the LoRA matrices $A$ and $B$ are merged into $W$, so the deployed model has exactly the same architecture and speed as the original MERT.
    \item \textbf{No catastrophic forgetting:} The frozen backbone retains its general music knowledge. Only the adapter matrices learn the chord classification task.
    \item \textbf{Easy experimentation:} Changing the rank $r$ (8 / 16 / 32) produces different model variants that can be compared in ablation experiments.
\end{itemize}

\subsection{Cascaded 3-Head Classification Architecture}

The key novelty of ChordSense Pro's AI model is the \textbf{Cascaded 3-Head} output architecture. Instead of predicting a chord directly from a flat list of 100+ class labels, the prediction is structured into three sequential heads:

\begin{enumerate}
    \item \textbf{Head 1 --- Root (12 classes):} Predicts the root note: C, C\#, D, D\#, E, F, F\#, G, G\#, A, A\#, B.
    \item \textbf{Head 2 --- Quality (6 classes):} Predicts the chord quality: major, minor, dominant, diminished, augmented, suspended. This head receives the MERT embedding \textit{plus} the logits from Head 1.
    \item \textbf{Head 3 --- Extension (8 classes):} Predicts the harmonic extension: none, maj7, min7, dom7, 9th, 11th, 13th, altered. This head receives the MERT embedding \textit{plus} the logits from Head 1 \textit{and} Head 2.
\end{enumerate}

This cascaded conditioning resolves the core spectral ambiguity problem. Am7 and C6 contain the same four pitch classes, so a flat classifier cannot distinguish them from the audio alone. But in the cascaded design, Head 1 first determines the root note (A vs.\ C). Head 3 then receives this root information as context, making it far easier to determine that the extension is ``min7'' (given root A) rather than ``6th'' (given root C).

\subsection{Training Dataset}

To provide broad chord vocabulary coverage, the following datasets are combined:

\begin{itemize}
    \item \textbf{McGill Billboard Dataset (1,300 songs):} Standard academic benchmark for pop and rock chord recognition, annotated in JAMS format.
    \item \textbf{JAAH --- Jazz Audio-Aligned Harmony (113 tracks):} Jazz recordings with extensive extended chord annotations (dominant 7th, maj7, min7, dim7, aug). Critical for Head 2 (Quality) and Head 3 (Extension) training.
    \item \textbf{ChoCo Corpus (20,000 tracks):} The largest open-license chord annotation corpus, including many jazz standards with 9th, 11th, 13th, and altered chord examples.
    \item \textbf{RWC Popular Music Database (100 tracks):} Japanese pop with full chord annotation.
    \item \textbf{Kaggle Guitar Chord Dataset v3 (7,000+ recordings):} Isolated guitar chord recordings.
    \item \textbf{VN Piano Extended Chord Dataset (custom):} A dedicated collection of Vietnamese piano recordings covering 7th through 13th chord types, manually recorded and pitch-shift augmented by the authors. This is the primary academic contribution of the project and will be published on Zenodo.
\end{itemize}

The combined dataset is split 70\% training / 20\% validation / 10\% test using stratified sampling to ensure all rare extended chord classes appear in each split.

\section*{Conclusion}
\addcontentsline{toc}{section}{Conclusion}

\subsection*{Summary of Achievements}

This project designs and implements \textbf{ChordSense Pro} --- an AI-powered, end-to-end interactive music practice platform that transforms raw audio chord detection into actionable musical intelligence within a unified practice workspace.

The system covers all user roles end-to-end:
\begin{itemize}
    \item \textbf{Musicians / Learners} import any song, receive a fully annotated harmonic analysis asynchronously (typically 15--45 seconds for a 3--4 minute song), and practice with A/B Loop, metronome, speed shift, Chord Dictionary, and, on the Pro tier, a connected MIDI keyboard.
    \item \textbf{Teachers and Students (Education package)} share a class repertoire and locked master charts, and teachers follow practice time, loop repetitions, and chord accuracy on a dashboard.
    \item \textbf{Music Platform Manager (Music PM)} monitors revenue and usage, configures subscription policy, handles user feedback, and flags AI quality problems from the Business Dashboard.
    \item \textbf{IT Administrator} manages infrastructure and datastores, protects the API gateway, monitors compute resources and audit logs, and controls the model deployment lifecycle from the Operations Console.
\end{itemize}

\subsection*{Key Technical Contributions}

\begin{itemize}
    \item \textbf{Cascaded 3-Head LoRA Architecture:} Resolves extended chord spectral overlap via sequential cross-head conditioning (Root $\to$ Quality $\to$ Extension).
    \item \textbf{VN Piano Extended Chord Dataset:} The first labeled benchmark for Vietnamese piano extended chords (7th through 13th), to be published on Zenodo.
    \item \textbf{Client-Side Harmonic Engine:} Zero-latency browser-side Roman numeral analysis, scale mapping, and Web MIDI chord detection with instant response to Edit Marker changes.
    \item \textbf{Focal Loss + Pitch-Shift Augmentation:} Addresses the extreme class imbalance between basic triads and rare extended chords in standard training datasets.
    \item \textbf{DDD Pipeline Architecture:} A domain-driven, bounded-context ETL pipeline that is dataset-agnostic and easily extensible to new audio sources.
\end{itemize}

\subsection*{Limitations}

\begin{itemize}
    \item \textbf{Piano-Only Scope:} Guitar and other instruments are planned as future extensions. The current model is optimized for piano timbre.
    \item \textbf{CPU Inference Latency:} The 200\,ms microphone Real-Time Practice Mode target (NFR-08) is conditional: it requires ONNX export and int8 quantization of a distilled model and sufficient client hardware. The Web MIDI path does not have this limitation.
    \item \textbf{Browser Support for Web MIDI:} The Web MIDI API is not available in every browser (for example Safari), so MIDI input is limited to supported browsers, with an on-screen keyboard as a fallback.
    \item \textbf{Dataset Size:} The VN Piano Extended Chord Dataset is smaller than large international benchmarks. Extended chord accuracy may be limited by the amount of available labeled data.
\end{itemize}

\subsection*{Future Work}

\begin{itemize}
    \item \textbf{Multi-Instrument Extension:} Fine-tune on guitar and ukulele datasets to support a broader range of musicians.
    \item \textbf{Mobile Application:} Extend the workspace to a native mobile app with offline chord recognition.
    \item \textbf{Sheet Music Export:} Integrate VexFlow-based chord sheet and lead sheet export in ChordPro format.
    \item \textbf{Adaptive Learning:} Use spaced repetition based on A/B Loop practice accuracy data to schedule chord review sessions automatically.
\end{itemize}
